## Summary

One paragraph. What is being proposed, and why should anyone care?

## Motivation

What problem does this solve? Describe the situation before this change and
why the current behavior is insufficient. Include concrete examples from real
use (for example, from a session in kk) where possible.

## Guide-level explanation

Explain the proposal as if teaching it to someone who uses kk but has not
read the implementation. Show how code looks before and after, and how a user
would think about the feature.

## Reference-level explanation

Describe the design in enough detail that it could be implemented: signatures,
types, invariants, error behavior, and how it interacts with existing
features. Note anything that is subtle or easy to get wrong.

## Drawbacks

Why should we *not* do this? Cost of implementation, extra API surface,
lost simplicity, and so on.

## Rationale and alternatives

- Why is this design the best among the alternatives considered?
- What other designs were evaluated, and why were they rejected?
- What is the impact of doing nothing?

## Outcome

Fill this in only when the proposal is settled. State whether it was accepted
or rejected, and give the reasoning that decided it. For a rejected proposal
this is the most important section: it is what stops the same request from
being raised again without new evidence. Leave the section out while the
proposal is still open.

## Unresolved questions

Points that must be settled before or during implementation. If there are
none, say so rather than leaving the section out.

## Future possibilities

How might this feature grow, and what related changes does it make easier or
harder later?
